A React client for the Go API you already wrote

Five routes, one fetch wrapper, no state manager. Plus four things the API has to give up before the UI can be honest about them.

TL;DR

Stack: Vite + React + TypeScript, Mantine for UI (AppShell, forms, modals, notifications in one dependency), TanStack Query for server state, React Router for five routes. Auth is a JWT in localStorage, decoded client-side for the user id — the API has no /me.

The CORS problem solves itself: the API has no CORS middleware, so the dev server proxies /api to it. Same origin, no preflight, no backend change.

Four API gaps block real features: posts carry no author name (feed would show UUIDs), nothing reports follow state (the Follow button can't survive a reload), description is VARCHAR(255) while the model allows 2000 (a guaranteed 500), and responses.JSON calls log.Fatal on an encode error. Fix those before Phase 3.

02How the pieces sit together

The only structural decision here is the dev proxy. The Go router wires up Logger and Auth and nothing else — there is no CORS middleware, so a browser on :5173 calling :4000 directly dies at the preflight. Vite's built-in proxy makes every call same-origin instead, which costs one config block and zero Go code.

UI libraryMantineAppShell, Modal, Autocomplete, useForm with validation, and notifications ship together. shadcn/ui would mean a Tailwind setup plus copying every component in by hand.

04Auth, end to end

There is no refresh token and the JWT lasts six hours, so expiry is a fact of life rather than an edge case. Two places handle it: the route guard checks exp before rendering, and the fetch wrapper treats any 401 as "the session is over".

On localStorage: it is XSS-readable. For a study project against a local API that is an acceptable trade, and the alternative — an httpOnly cookie — needs the backend to set cookies and handle CSRF, which it currently does not. Worth knowing you made the choice rather than discovering it later.

05What the API has to fix first

Four of these are real blockers for features you asked for. Each fix is small; none of them are frontend problems you can paper over cleanly.

api change

Posts carry no author name

Post has authorId and nothing else, so a feed card can only render a UUID. The feed is the first screen after login — this is not cosmetic.

fixJoin in the four post queries in api/src/posts/repository.go: inner join users u on u.id = p.author_id, select u.nickname, add AuthorNickname to the model. The feed query already joins followers, so the shape is familiar.

altThe frontend could fetch GET /users once and build an id → nickname map. It works, it needs no Go, and it downloads every user in the database to render one screen. Take the join.

api change

Nothing reports follow state

GET /users/{id} returns name, nickname, email, timestamps. There is no follower count and no way to ask "am I following this person". The Follow button can toggle optimistically and then render the wrong label on every reload — which makes the follow feature look broken even though the writes land.

fixExtend that endpoint with followersCount, followingCount and isFollowing, the last one computed against the token's user id — one extra query over the followers table.

bug

description is VARCHAR(255), the model allows 2000

PrepareCreate accepts descriptions up to 2000 characters; migration 000003 declares the column as VARCHAR(255). Anything in between passes validation and dies at the insert as an unhandled 500. A textarea is the whole point of a post composer, so the UI will hit this on day one.

fixNew migration: alter table posts alter column description type varchar(2000) — or drop the model's limit to 255 and enforce the same number in the form. Either way the two numbers must match, and the frontend counter reads from whichever you pick.

bug

responses.JSON can kill the server

On a JSON encode failure it calls log.Fatal, which exits the process. One malformed response takes the whole API down — an unpleasant thing to discover while clicking around a new UI.

fixSwap it for log.Println. One word.

frontend handles it

No /me, no CORS, singular /post

The missing /me is covered by decoding the JWT. CORS is covered by the dev proxy. The /post vs /users naming inconsistency is ugly and completely harmless — the client hardcodes both either way. Leave it.

07Build order

Each phase ends with something you can click. The phases are genuinely sequential — phase 3 renders data the API does not return yet, so the backend fixes have to land in between.

1
Scaffold and get logged in

Vite + TS, Mantine provider, QueryClient, router. Write api.ts and vite.config.ts proxy. Build /login, /register, RequireAuth, Shell.

Ship: log in, land on an empty feed, reload without being kicked out.
2
Feed and composing

GET /feed into PostCard, the PostForm modal wired to POST /post, invalidate the feed query on success. Empty state that says to go follow someone — the feed excludes your own posts, so a new account sees nothing and that needs explaining on screen.

Ship: post something, see a followed user's posts.
·
Backend interlude

The four fixes from section 05. Roughly an hour: one join across four queries, one endpoint extension, one migration, one word.

Ship: cards can show a name; a profile can answer "am I following you".
3
Profiles, ownership and following

/users/:id with header, counts, that user's posts. Follow/unfollow with an optimistic toggle rolled back on error. Owner-only edit and delete on PostCard, reusing PostForm. Header autocomplete for finding people.

Ship: every requirement except password change.
4
Settings

Profile form — remember PUT /users/{id} validates name, nickname and email, so always send all three. Password card posting {currentPassword, newPassword}, with the API's message surfaced verbatim in a notification when the current password is wrong.

Ship: feature-complete against your list.
5
The unglamorous pass

Loading skeletons, empty states, the 401 path exercised by hand, form-level error display, the 50-character title counter and whatever the description limit ended up being.

Ship: it stops feeling like a prototype.

08Deliberately not built

  • Likes, comments, avatars, images — no tables, no columns, no storage. Adding them is a backend project, not a UI one.
  • Infinite scroll and pagination — no endpoint takes a limit or offset. Add it when a feed actually gets long enough to hurt.
  • A state manager — TanStack Query owns server data and the token is one string. There is nothing left for Redux to hold.
  • SSR / Next.js — an authenticated dashboard behind a login has no SEO to gain and no first-paint problem worth a framework.
  • Refresh tokens and silent renewal — six hours, then log in again. Real work in the backend for a study project's convenience.
  • A test suite — one Vitest file over api.ts, because error unwrapping and the 401 path are the only logic in the app that is not "render what the server said". Component tests can wait for a component that earns one.
  • Delete-account UI — the endpoint exists; you did not ask for the screen.
